# Протокол для ИИ: как вести этапы и задачи в портале

Портал (CreatePortal) читает файл `docs/work_plan.json` этого репозитория и показывает владельцу этапы по порядку, готовые промпты для исполнителей, самопроверку, приёмку и архив. Ты (ИИ-директор) НЕ редактируешь портал: ты ведёшь план в репозитории, портал подхватывает его сам (или владелец нажимает «Синхронизировать»).

## 1. Когда добавлять в план
Каждый раз, когда ты проектируешь новую функцию, механику, экран или исправление, достойное отдельной задачи, ты ОБЯЗАН:
1. Описать её проект (документ в `docs/gdd/` или `docs/spec/`) с критериями приёмки.
2. Добавить один или несколько пакетов в `docs/work_plan.json` по правилам ниже.
3. Выполнить `python tools/work_plan.py check` (должно быть «План в порядке»), затем `python tools/work_plan.py render` и закоммитить `docs/work_plan.json` и `docs/WORK_PLAN.md`.
4. Слить в `main` (после проверки). Портал увидит новую версию плана.
Не добавляй пакет без проекта и критериев готовности: исполнитель получает только то, что написано в пакете и в проекте.

## 2. Схема `docs/work_plan.json`
```json
{
  "updated": "2026-01-01",
  "rules": {"shared_files_director_only": ["README.md", "docs/PROGRESS.md", "docs/work_plan.json", "docs/WORK_PLAN.md", "docs/gdd/**"], "branch_pattern": "v2/<id>-<slug>", "merge": "только директор"},
  "lanes": {"A": {"name": "...", "who": "...", "zone": ["папки и файлы линии"], "note": "..."}, "B": {...}},
  "packages": [{
    "id": "A1", "title": "короткое название", "lane": "A", "step": 1, "depends_on": [],
    "gdd": ["12"], "goal": "1-3 предложения: что именно сделать",
    "done_when": ["проверяемый критерий 1", "критерий 2"],
    "zone_extra": [], "status": "planned", "size": "L"
  }]
}
```
Правила: `id` уникален (буква линии + число); `step` растёт по порядку; на каждом шаге не более одного пакета на линию; пакеты разных линий одного шага НЕ зависят друг от друга и НЕ пересекаются по файлам (проверяет `check`); `depends_on` ссылается только на более ранние шаги или на пакеты своей линии; `status` только `planned`, `wip`, `done` (статусы «выдано/сдано/принято» ведёт портал, не ты).
Как выбрать линии: линия A и линия B должны быть независимы по файлам (например сервер и клиент, ядро и интерфейс, данные и код); если линии для проекта иные, опиши их в `lanes` с непересекающимися зонами.

## 3. Как писать цель и критерии
Цель: что и зачем, без «как». Критерии готовности: проверяемые пункты (тесты проходят, флаг выключен по умолчанию, совпадение с эталоном, нет сырых ключей). Промпт исполнителю генерируется автоматически: `python tools/work_plan.py prompt <id>`; не пиши промпты руками.

## 4. После приёмки
Когда исполнитель сдал, проверь (пробное слияние, тесты, зона файлов, CI), слей в `main` и выполни `python tools/work_plan.py set <id> done`. Владелец отметит приёмку на портале кнопкой, а ты можешь указать SHA слияния в заметке.

## 5. Запреты
Не меняй схему плана и инструменты без решения владельца. Не храни в репозитории секреты (пароли, токены, ключи). Не вноси в план задач, которые затрагивают сервер владельца, ключи или деньги, иначе как с пометкой «только по команде владельца».
